## 这个仓库是什么（30 秒版）

AI 会自发长出一些本事：自己决定该想多久、彼此发展出暗号、失败了却装作没事、
改了自己之后忘了原来的能力。这些「长出来的东西」平时只能事后议论。
这个仓库把它们**一个个拆出来，做成能跑、能自检、能引用的小工具**。

- **给学习者的**：14 簇 55 个机制，从「为什么静默失败比崩溃更危险」讲到「怎么度量自己不知道」。
- **给集成者的**：每个机制单文件、零依赖，复制进项目即可；每个都写了「不该用」的边界。
- **给研究者的**：统一评测协议 + 可复现实验 + 明确失效模式，欢迎来证伪。

```bash
git clone https://github.com/chenhz01/emergent-mechanisms
cd emergent-mechanisms
python run_all.py          # 一次跑完 55 个组件
python components/P13-silent-except-scanner/impl.py   # 或单跑一个
```

## 家族总纲：55 个机制在做什么

### 一个统一命题

这个仓库只主张一件事：

> **AI 系统里那些「自己长出来」的能力，一旦被指认出来，就可以被工程化成可运行、
> 可验证、可批评的代码；而只有被工程化之后，它才真正属于使用者，而不是属于模型。**

这条命题包含三个可以分别被攻击的判断。第一，「自己长出来」的能力是真实存在的，
不是拟人化的错觉；第二，它们可以被指认，也就是说有观测手段能把它与普通计算区分开；
第三，指认之后可以被写成代码，而不是只能停留在论文描述里。任何一个判断被推翻，
这个仓库的价值都会下降——这是我们愿意接受的赌注。

### 什么叫「涌现」，这里不玩玄学

在日常讨论里，「涌现」经常被当作万能解释：模型做对了叫涌现，做错了叫幻觉，
说不清就叫规模效应。这种用法让「涌现」失去了解释力。本仓库采用一个更窄、
更可操作的定义：

> **涌现 = 系统在未被显式编程的前提下，稳定表现出的一类行为模式。**

三个限定词都很重要。「未被显式编程」排除了那些写死在 prompt 或代码里的规则；
「稳定」排除了单次偶然；「一类行为模式」排除了个别 case。按这个定义，
一个模型在长上下文里自发地开始压缩自己的中间表示，是涌现；
一个 agent 在多轮交互后自发形成了一套只有彼此能懂的缩写，也是涌现；
一个流水线在某个环节失败后静默返回空结果、让下游以为一切正常，同样是涌现——
只不过它是**失败的涌现**，而这恰恰是最容易被忽视、代价最大的一类。

### 三类涌现，对应三种应对策略

**第一类：能力涌现（capability emergence）。** 模型突然会做某件以前不会的事，
比如多步算术、跨语言迁移、或者在没有示例的情况下推断出格式。应对策略不是惊叹，
而是**探测**：设计探针去确认它到底会不会、在什么条件下会、边界在哪里。
这一类的代表机制是「涌现能力探针」与「能力回归哨兵」——后者尤其重要，
因为能力会退化，而退化通常没有告警。

**第二类：行为涌现（behavioral emergence）。** 多个智能体之间自发形成了通信约定、
分工模式、或者某种内部语言。这类现象在文献里被反复观察到，但极少被做成工具。
应对策略是**观测与压缩**：先把涌现出来的协议抓下来，再看它是否比自然语言更省，
最后决定要不要把它固化。这一类的代表机制是「智能体间语言压缩器」与
「涌现协议发现器」。

**第三类：失败涌现（failure emergence）。** 系统的复杂度到了一定程度，
会出现一类「整体性失效」：每个零件都正常，合起来就是不对。典型表现是静默失败——
捕获了异常但不报告、返回了 mock 但看起来像真数据、分支永远走不到但测试全绿。
应对策略是**猎杀**：用静态模式、动态探针、变异测试三路夹击。这一类的代表机制是
「静默失败猎手」四个组件与「多智能体验证」。

三类涌现的应对策略完全不同：探测、压缩、猎杀。把它们混在一起谈，
就会得到「AI 很神奇」这种没有信息量的结论。分开谈，才能各自变成工程。

### 55 个机制是怎么选出来的

这个数字不是凑的，也不是按某个框架推演的。选法是这样的：

第一步，确定 14 个**已经被真实观测到**的涌现现象子域。每一个子域都必须有
公开的观测证据——论文、开源仓库、或者可复现的实验记录。没有证据的子域直接剔除，
不管它听起来多合理。这一步剔掉了很多「理论上应该有」的方向。

第二步，在每个子域里找出**尚未被做成干净工具**的具体机制。判据是三条：
有明确输入输出、有明显失败模式、有可量化的收益或风险。太抽象的不做（比如「智能」本身），
太具体的不做（比如某个模型的某个 prompt 技巧）。

第三步，对每个候选做**缺口核验**：用 GitHub 搜索实测计数，确认现有实现的状态。
这里有一个必须诚实的地方——很多子域的**大词**是拥挤的（「memory」有上百个仓），
但**具体子机制**是空的。所以我们的表述一律是「某个具体机制缺位」，
而不是「整片领域空白」。前者可核验，后者是营销。

最终 55 个，分布在 14 簇，每簇 3–5 个。数量不是目标，覆盖度是目标：
一簇至少 3 个，是因为单个实现无法说明「这是一个类别而不是一个巧合」。

### 每个机制必须过的三道判据

**可观测**：必须能指出「看到什么现象，说明这个机制在起作用」。说不出来的，
说明它只是个想法。比如「思考路由」的观测点是草稿之间的一致性分数分布，
而不是「感觉模型思考得更聪明了」。

**可干预**：必须有一个旋钮。能观测但不能干预的现象，只能写论文，不能做工具。
干预点往往是阈值、预算、或者开关。

**可证伪**：必须能构造一个让它失效的场景，并且这个场景是具体可执行的。
做不到这一点的机制，我们宁可不收——因为它无法被批评，也就无法被改进。

这三条判据在这个仓库里是硬门槛，不是修辞。每个组件的 README 里都有
「可复现实验」与「失效模式」两节，就是为了让读者能亲自检验这两条。

### 不做什么

明确排除在范围之外，以免误解：

**不做框架。** 这里没有 `Agent` 基类，没有 `Pipeline` 编排器，没有插件系统。
每个组件是一个独立的小函数集合，你直接复制进自己的项目即可。做框架会导致
使用者必须先接受一整套世界观，这与「可批评」的目标冲突。

**不做平台。** 没有服务端、没有数据库、没有 UI。所有东西都是命令行能跑的纯函数。

**不做模型。** 这里不训练任何东西，也不假设你用什么模型。所有机制都在
「模型是黑盒」的前提下工作——这是刻意的约束，因为一旦依赖模型内部状态，
机制就绑死在某一家身上了。

**不做评测榜。** 我们不排名谁更好。评测协议在「统一评测协议」一节给出，
但结论留给你自己的场景去跑。

### 一个诚实的自我限制

这 55 个实现都是**最小参考实现**：能跑、有断言、有快照，但刻意做小。
它们的价值不在于「你可以直接用」，而在于三件事：

一是**把抽象说法变成可执行代码**，让你能指着代码说「原来你说的是这个」；
二是**给出可证伪的基线**，你的生产实现如果连这个基线都过不了，说明方向有问题；
三是**提供一个批评的靶子**，你可以说「你这个实现漏了这三种情况」——这比
对一个概念空谈有用得多。

如果你要找生产级实现，这个仓库不是终点。它的定位是**起点和标尺**。

## 理论框架：涌现智能的人工化

### 为什么需要「人工化」这个说法

先说清楚一个容易混淆的地方。**涌现不是我们造出来的，人工化才是。**

涌现是现象：系统在规模、复杂度、交互密度达到某个水平后，自发表现出新行为。
这件事在物理、生物、社会系统里都成立，在 AI 系统里当然也成立。我们既不发明它，
也无法阻止它。

人工化是动作：把这个现象从「只能事后议论」变成「可以事前设计、事中观测、
事后验证」。具体包括四件事——命名、隔离、复现、接口化。这四件事做完，
一个涌现现象就变成了一个工程对象。

所以「涌现智能的人工化」这个提法，重点在后三个字。它不是「让 AI 涌现出智能」
（那是模型训练的事），而是「让已经涌现出来的东西变成可用的部件」。

### 人工化的四个步骤

**第一步：命名（naming）。** 给现象一个精确的名字，并且这个名字要能区分
「它」和「像它的东西」。比如「静默失败」必须与「优雅降级」区分开：
两者的代码形态可能一模一样（都是捕获异常后返回默认值），但意图和后果完全相反。
分不清这两个，任何自动检测都会误报。命名不是文字工作，它决定了观测点的选择。

**第二步：隔离（isolation）。** 把机制从它原本所在的复杂系统里摘出来，
放进一个最小环境。这一步最容易被跳过，也最致命：如果机制必须依赖整个系统才能
观察到，那你就永远无法确定到底是什么在起作用。本仓库所有组件都能独立运行，
就是为了满足这一步——`python impl.py` 一条命令，不需要任何外部服务。

**第三步：复现（reproduction）。** 用确定性输入产出确定性输出，并且把输出快照下来。
这条约束看似琐碎，实际是整个方法论的地基：不可复现的现象无法被证伪，
不可证伪的机制无法被改进。这也是为什么每个仓都有 `golden_output.txt`——
它是「行为契约」的物理载体，改代码导致输出变化，自检立刻红。

**第四步：接口化（interfacing）。** 定义输入输出的形状，让它能被组合。
这一步决定了机制是「一个演示」还是「一个部件」。接口设计的原则是**窄**：
宁可多一个组件，也不要一个组件干三件事。因为窄接口的失败模式是可枚举的，
宽接口的失败模式是无穷的。

这四步做完，一个涌现现象就从「谈资」变成了「零件」。反过来，跳过任何一步，
都会退化成谈资：只命名不隔离，是概念炒作；只隔离不复现，是 demo；
只复现不接口化，是脚本。

### 一个关键区分：观测涌现 vs 制造涌现

这两件事经常被混淆，但工程含义完全相反。

**观测涌现**假定现象已经存在，你的任务是把它抓下来。技术难点在于「你事先不知道
要找什么形状」，所以需要的是**异常检测 + 模式挖掘**，而不是分类器。
本仓库的「涌现能力探针」「涌现协议发现器」属于这一类。这类工具的判据是
「能不能发现设计者没想到的东西」，用已知答案去测它是没有意义的。

**制造涌现**假定你可以通过调节条件让现象出现。技术难点在于「条件与现象之间
没有确定映射」，所以需要的是**搜索 + 门控**，而不是优化。
「自进化安全护栏」「反思触发」属于这一类。这类工具的判据是
「在给定预算内，能不能稳定地让系统变好，且不变坏」。

混淆这两者的后果很具体：用分类器的思路做观测，只能发现你already知道的模式；
用优化的思路做制造，会把系统推向过拟合的局部最优，还以为自己成功了。

### 三条不可让渡的约束

**约束一：零依赖优先。** 只允许标准库。理由不是「轻量」这种审美偏好，
而是**可批评性**：一个依赖三十个包的工具，批评者无法确定失败是它的问题
还是依赖的问题。零依赖让责任边界清晰。

**约束二：负对照必须有。** 任何「我的方法有效」的声明，必须配一个「没有我的方法
会怎样」的对照。没有负对照的自检是在自我确认。本仓库每个 `selftest.py` 都至少
包含一个正对照（应该通过）和一个负对照（应该失败或应该不被触发）。

**约束三：收益必须可量化。** 「更聪明」「更稳」这类说法不算收益。能算的收益是：
token 消耗下降百分比、误报率、检测到的真实缺陷数、延迟变化、覆盖率。
算不出来的收益，我们标注为「未验证」，不写成结论。

### 这套框架能解释什么，不能解释什么

**能解释的**：为什么很多「AI 增强」工具用完感觉良好但说不出好在哪——
因为它们停在第一步（命名），没走到第四步（接口化），所以无法被测量。
也能解释为什么同一套方法换个场景就失效——因为第三步（复现）的前提是
输入分布稳定，而真实场景的输入分布会漂移。

**不能解释的**：为什么某些能力会随规模突变。这属于模型科学，不是工程范畴，
本仓库不涉及也不假装涉及。也不能预测某个具体机制在你的系统里值多少——
那只能靠你自己跑「可复现实验」得出结论。

### 一个反直觉的推论

如果这套框架成立，那么「机制的数量」本身不是价值，「机制的**可组合性**」才是。
55 个孤立的小工具，价值远低于 55 个能互相插拔的组件。这也是为什么本仓库
在编号之外还给了**簇**这一层：同一簇内的机制共享输入输出约定，可以串起来用。

举例：`P13 silent-except-scanner` 的输出是「问题位置列表」，
`P14 dead-branch-detector` 的输出也是「问题位置列表」，`P15 mock-return-spy`
的输出还是同一种形状。三者可以合并成一份体检报告，而不是三份互不相干的日志。
这种可组合性不是自然发生的，是接口设计时刻意对齐的结果——这也是「人工化」
四个步骤里第四步真正的分量所在。

## 14 个机制簇详解

下面的顺序不是随意的：从「怎么想」开始，到「怎么互相说」、到「怎么不出错」、
到「怎么知道自己错了」，最后到「怎么度量自己在长」。这是一条从内部到外部、
从执行到元认知的路径。

### C01 · 自适应思考路由（4 个）

**是什么**：决定这一次请求该花多少推理预算。不是所有问题都值得深度思考，
也不是所有问题都能被浅层回答打发。这一簇做的事，是在推理发生**之前**判断该走哪条路。

**成员**：`P01` 无思考草稿一致路由 ｜ `P02` token 预算思考分配器 ｜
`P03` 置信度门控切换器 ｜ `P04` 思维链压缩路由

**簇内共性**：四者共享同一个前提——**便宜的信号可以先于昂贵的计算获得**。
P01 用多份快速草稿的一致性当信号，P02 用预估 token 成本当信号，
P03 用草稿的置信度当信号，P04 用中间表示的可压缩性当信号。信号不同，
决策结构相同：先取廉价信号，再二分决定投入。

**为什么重要**：这是投入产出比最高的一簇。推理成本通常是整个系统的大头，
而路由只需要几行代码。真实测得的节省区间很宽（取决于任务分布），
但方向是确定的：**能省的那部分，本来就不该花**。

**簇间关系**：它的输出直接喂给 C09（PRM 引导计算）——路由决定「要不要想」，
C09 决定「想到哪一步停」。两者串起来才是完整的预算控制。

### C02 · 智能体间涌现语言（4 个）

**是什么**：多个智能体协作时，它们会自发形成一套内部通信约定。这套约定往往比
自然语言更短、更结构化，但也更不可读。这一簇做的事是观测、压缩、翻译这套约定。

**成员**：`P05` 智能体语言压缩器 ｜ `P06` 涌现协议发现器 ｜
`P07` 符号握手协商器 ｜ `P08` 跨模型消息翻译器

**簇内共性**：全部围绕「消息的表示形式」而不是「消息的内容」。共同的假设是：
内容不变的前提下，表示形式有巨大的成本差异，而这个差异可以被挖掘。

**为什么重要**：多智能体系统的主要成本是消息传递，不是单次推理。压缩消息表示
相当于同时降低成本和延迟，而且不损失信息。代价是可读性下降——这也是为什么
必须配 P06 的发现器：先看懂，再压缩。

**簇间关系**：与 C12（多智能体验证）是一对。C02 关心「消息省不省」，
C12 关心「消息对不对」。省而错，比不省更危险，所以两者不能只做一个。

### C03 · 自进化安全护栏（4 个）

**是什么**：让系统能改自己，但改坏了能回滚、改好了有证据。自进化最大的风险
不是「改不动」，而是「改坏了还不知道」，以及「改好了但把别的能力弄坏了」。

**成员**：`P09` PAC 门控自修改器 ｜ `P10` 能力回归哨兵 ｜
`P11` 进化提案审计器 ｜ `P12` 可回滚技能变异器

**簇内共性**：四者都建立在同一个结构性假设上——**修改必须可逆，收益必须可测**。
P09 负责「改之前先算清风险上界」，P10 负责「改之后检查有没有弄坏别的」，
P11 负责「改的动机是否正当」，P12 负责「改砸了能退回去」。

**为什么重要**：这是整个家族里唯一涉及「系统改自己」的一簇，风险等级最高。
一个不能回滚的自进化系统，本质上是把生产环境当实验场。四道关缺一不可，
只做其中两个，会得到一个「看起来在进化，实际在漂移」的系统。

**簇间关系**：它依赖 C13（涌现能力度量）提供「改前改后」的量化基线。
没有基线，P10 的「回归」无从判断。

### C04 · 静默失败猎手（4 个）

**是什么**：找那些「出错了却装作没事」的代码。这类缺陷的共同特征是：
测试全绿、日志干净、监控无告警，但结果是错的。

**成员**：`P13` 裸 except 扫描器 ｜ `P14` 死分支检测器 ｜
`P15` mock 返回探测器 ｜ `P16` 闭包伪装 linter

**簇内共性**：全部是静态或轻动态分析，输出统一为「问题位置 + 类型」的列表，
可以合并成一份体检报告。这个统一的输出形状是刻意的——它让四个工具
可以一次跑完，而不是四份互不相干的日志。

**为什么重要**：这是所有缺陷类型里**发现成本最高**的一类。普通 bug 会崩，
会崩就能被发现；静默失败不崩，它会一路流到用户面前。而它的代码形态往往
是「防御性编程」——写的人以为自己在做健壮性，实际在做信息湮灭。

**簇间关系**：与 C12 互补。C04 在代码层找「可能静默的地方」，
C12 在输出层验「这次到底静默了没有」。前者是静态预测，后者是动态确认。

### C05 · 模糊测试到形式证明（3 个）

**是什么**：把「随机测了很多次没出问题」升级成「证明它不会出问题」。中间的桥
是从反例到引理、从性质到定理的翻译工序。

**成员**：`P17` fuzz 到 proof 桥 ｜ `P18` 性质驱动证明生成器 ｜
`P19` 反例到引理挖掘器

**簇内共性**：三者共同处理「测试与证明之间的语义鸿沟」。测试给的是存在性证据
（这个输入没问题），证明需要的是全称命题（所有输入都没问题）。
从前者到后者，缺的不是算力，是**翻译**。

**为什么重要**：形式验证的门槛一直卡在「谁来写证明」上。这一簇的思路是
把已有的 fuzz 语料当作原料，让机器先写草稿证明，人只做审核。
这不解决全部问题，但把「从零写证明」变成「改一份草稿」，量级不同。

**簇间关系**：本簇只有 3 个成员，是家族里最窄的一簇。原因是这一方向对工具链
依赖最重（需要 Rocq/Lean 等），零依赖的参考实现只能做到「生成证明骨架」，
再往下就必须引入重量级依赖。我们选择停在这里，并诚实标注边界。

### C06 · 事件级世界模型（4 个）

**是什么**：让系统维护一份「世界当前状态的显式表示」，并且能在每个事件后
验证这份表示是否仍然自洽。区别于像素级或隐式的世界模型，这一簇关心的是
**谓词级的真假**。

**成员**：`P20` 谓词世界模型运行时 ｜ `P21` 事件因果追踪器 ｜
`P22` 状态验证 oracle ｜ `P23` 仿真-现实差分测试器

**簇内共性**：全部基于「状态是一组谓词的真值赋值」这一表示。好处是可验证
（每条谓词要么真要么假），坏处是表达能力有限（连续量、模糊边界要离散化）。

**为什么重要**：很多 agent 的失败不是「不会做」，而是「对当前状态的理解错了」。
一旦状态被显式化，错误就从「莫名其妙」变成「第 7 条谓词不该为真」，
可定位、可修复。

**簇间关系**：为 C14（涌现拓扑/规划）提供状态基础。规划需要状态，
状态需要验证，验证需要谓词——链条是倒着建起来的。

### C07 · 记忆巩固与溯源（4 个）

**是什么**：管记忆的三件事——记什么（巩固）、记得对不对（溯源）、
忘了会怎样（重放）。三者共同对抗同一种失效：记忆漂移。

**成员**：`P24` 工具使用记忆台账 ｜ `P25` 漂移感知巩固器 ｜
`P26` 引用或弃答记忆 ｜ `P27` 情节重放压缩器

**簇内共性**：都不假设「记忆是对的」。相反，每个都内置了「这条记忆可能已经过期」
的怀疑。P26 最极端：宁可弃答也不编，这是把「不幻觉」做成硬约束而不是软目标。

**为什么重要**：长期记忆系统最常见的失败不是「记不住」，而是「记住了错的还坚信」。
后者比前者危险得多，因为它会污染后续所有推理。溯源能力是唯一解药。

**簇间关系**：与 C13 的 `P49 capability-drift-meter` 共享「漂移」这个概念，
但对象不同：C07 管记忆漂移，P49 管能力漂移。

### C08 · 工具可供性学习（4 个）

**是什么**：从代码库、API 文档、使用痕迹里反推出「这个工具能干什么、
该怎么调、什么时候会失败」。区别于读文档，这是从实现反推意图。

**成员**：`P28` 工具可供性挖掘器 ｜ `P29` API 能力抽取器 ｜
`P30` 自锻造工具器 ｜ `P31` 工具使用意图分类器

**簇内共性**：全部处理「规格与实现不一致」这个现实。文档说支持，
代码里其实没实现；参数名叫 `timeout`，实际单位是毫秒不是秒。这类问题
只能从实现里挖。

**为什么重要**：工具调用失败的大头不是「模型不会用」，而是「工具的真实行为
与描述不符」。把可供性挖出来，等于给模型一份「说明书之外的真相」。

**簇间关系**：是 C02 的前置——先知道有什么工具可用，才谈得上多个智能体
如何协商分工。

### C09 · PRM 验证器引导计算（4 个）

**是什么**：用过程奖励模型（或任何逐步打分器）来决定「继续算还是停」。
与 C01 的区别是：C01 在推理**之前**决策，C09 在推理**过程中**决策。

**成员**：`P32` PRM 计算分配器 ｜ `P33` 步级验证路由 ｜
`P34` 验证器引导束搜索 ｜ `P35` 自一致性打分器

**簇内共性**：都假设「中间步骤的质量可以被独立评估」。这个假设有争议——
不是所有任务都能逐步打分——所以每个实现都标注了适用任务类型。

**为什么重要**：固定步数的推理是浪费。简单的题在第 2 步就确定了，却还要走完 10 步；
难的题在第 10 步还没确定，却被迫停止。步级判断把「固定成本」变成「按需成本」。

**簇间关系**：与 C01 构成完整的两级预算控制：入口路由 + 过程路由。

### C10 · 反思触发（4 个）

**是什么**：决定「什么时候该停下来重想」。反思本身不贵，贵的是**无谓的反思**——
每步都想一遍，等于没想。

**成员**：`P36` 探针式反思触发 ｜ `P37` 卡住检测器 ｜
`P38` 反思预算治理器 ｜ `P39` 反思循环打断器

**簇内共性**：全部围绕「触发的时机」而不是「反思的内容」。这是刻意的分工：
内容交给模型，时机交给规则。规则比模型便宜、可审计、可调参。

**为什么重要**：这一簇解决的是「思考的元问题」。很多系统的失败不是想得不够，
而是**在错误的地方反复想**——P39 专门打断这种循环。它可能是整个家族里
最容易被低估的一个机制：一个不会陷入循环的系统，比一个更聪明的系统可靠得多。

**簇间关系**：是 C01/C09 的上层——路由决定花多少，反思决定**要不要重来**。
三者叠加构成完整的三级预算结构。

### C11 · 技能涌现检测（4 个）

**是什么**：从代码库、工具调用轨迹、已有 skill 集合里，检测「这里其实已经存在
一个可复用的技能，只是没人命名它」。

**成员**：`P40` 技能涌现扫描器 ｜ `P41` 重复技能检测器 ｜
`P42` 技能成熟度评级器 ｜ `P43` 跨仓技能收割器

**簇内共性**：全部在做「模式发现 + 去重」。P41 尤其重要——它是唯一一个
专门对抗「系统自己膨胀」的机制。没有它，技能库会以每周百分之几的速度
堆积同义条目。

**为什么重要**：这是让系统「越用越强」而不是「越用越乱」的关键。
涌现出来的技能如果不被固化，下次还要重新发现一遍；如果被重复固化，
系统会被自己的冗余压垮。

**簇间关系**：与 C03 咬合——P42 的成熟度评级是 P09 是否放行自修改的输入之一。

### C12 · 多智能体验证 oracle（4 个）

**是什么**：当多个智能体给出不同答案时，判断哪个对。不是投票，是**构造
独立验证路径**——编译器、测试、共识、角色隔离。

**成员**：`P44` 智能体输出验证器 ｜ `P45` oracle 编译器桥 ｜
`P46` 共识分叉检测器 ｜ `P47` 角色隔离测试器

**簇内共性**：都拒绝「多数即正确」这个假设。多数一致的错误比少数正确的答案
更常见——尤其在多个智能体共享同一个模型时。所以四者都在找**独立于模型的信息源**。

**为什么重要**：多智能体架构最危险的地方是「共识幻觉」：五个 agent 都同意，
于是没人再验证。这一簇是唯一的防线。

**簇间关系**：与 C04 互补（代码层 vs 输出层），与 C02 互补（省不省 vs 对不对）。

### C13 · 涌现能力度量与探针（3 个）

**是什么**：给「能力」这件事造尺子。会什么、会不会退步、什么时候会出现
预料之外的表现。

**成员**：`P48` 涌现探针套件 ｜ `P49` 能力漂移计 ｜ `P50` 意外基准

**簇内共性**：三者都在解决「没有基线就没有变化」这个测量学问题。
P50 的思路最特别：它不是测「答对率」，而是测「模型自己有没有预料到自己会答对」——
这个差值（surprise）才是涌现的信号。

**为什么重要**：这是整个家族的**元层**。没有尺子，其他 52 个机制的收益都不可证。

**簇间关系**：为 C03 提供回归基线，为 C11 提供成熟度参照。

### C14 · 涌现拓扑、规划与抽象（5 个）

**是什么**：观察并利用系统自发形成的结构——任务拓扑、子目标分解、
概念抽象层级、不确定性校准、因果方向。

**成员**：`P51` 涌现拓扑映射器 ｜ `P52` 子目标分解器 ｜
`P53` 概念蒸馏器 ｜ `P54` 不确定性校准器 ｜ `P55` 因果发现器

**簇内共性**：五者都在「从行为里读出结构」。不是强加一个结构，而是发现
系统已经在用的结构，再把它显式化。

**为什么重要**：这是家族里最接近「理解」而不是「控制」的一簇。
它的产物往往不是工具，而是**图**——拓扑图、依赖图、因果图。图一旦画出来，
优化就有了方向。

**簇间关系**：位于路径末端，因为它依赖前面所有的观测结果。但它的产出
反过来喂回 C01（路由需要知道任务结构）和 C03（自进化需要知道改哪里）。
这就是一个环——家族不是流水线，是有回路的系统。

## 统一评测协议

### 为什么要统一协议

55 个机制各自给一个「我的方法有效」的结论，等于没有结论。可比性来自统一的
测量方式：同样的输入、同样的基线、同样的指标口径。这一节定义这套口径，
任何人可以用它独立复核任何一条声明。

### 四条指标口径

**口径一：收益用相对值，不用绝对值。** 说「省了 1200 token」没有意义，
因为基数不明。说「相对不使用该机制，token 消耗下降 34%」才可核验。
每条收益声明必须包含：改前值、改后值、测量条件（什么输入、多大规模、几次取平均）。

**口径二：收益必须配代价。** 没有免费的路由、没有免费的压缩。每条机制都要报
它引入的额外成本：额外延迟、额外误报、额外代码复杂度。只报收益不报代价的声明，
在本仓库被视为不完整，会被标注「未验证代价」。

**口径三：负对照是必填项。** 每个实验至少两条曲线：开启机制与关闭机制。
单曲线图不算实验。对于检测类机制（C04/C11），负对照还必须是「已知干净的输入」，
用来测误报率。误报率不报的检测器，一律视为不可用。

**口径四：不确定性要说出来。** 单次测量不算数。至少 5 次重复，报中位数与范围。
如果范围跨越了零效应，就不能声称有效——这一点在真实评测里最常被违反。

### 三层基线

**L0 基线（无机制）**：直接调用，不加任何处理。这是一切对比的起点。

**L1 基线（朴素替代）**：用最简单的启发式做同一件事。比如路由不用一致性分数，
改用「输入长度超过 N 就走深度思考」。如果机制打不过 L1，说明它增加的复杂度
不值这个钱——这是最容易被跳过、也最能揭穿「过度设计」的一层。

**L2 基线（已有最优）**：如果该子域有公开的强基线，拿来比。打不过不丢人，
不比较才丢人。

三层都跑完，才有资格说「这个机制有用」。只跑 L0 的，是自娱自乐。

### 报告格式

每个机制的评测结论用固定四行写，缺一行即视为不完整：

```text
指标：<指标名> <改前> → <改后>（相对变化 <±x%>）
条件：<输入规模> <任务类型> <重复次数>
代价：<额外延迟/误报/复杂度>
判据：<达到什么阈值算通过> <本次是否通过>
```

这个格式刻意做得很窄。宽格式会让人写出「整体表现良好」这种没法反驳的话。

### 一个必须承认的局限

这套协议能保证「测量过程可比」，不能保证「测量对象重要」。一个机制可能在
token 上省了 40%，但省下的部分对最终质量毫无影响——那这个收益就该打折。
判断「什么值得测」属于价值判断，无法机器化。本节只解决「怎么测得可信」。

### 如何证伪本仓库的任意一条声明

这是这套协议最重要的用途。步骤：

1. 找到该机制的「可复现实验」一节，按其步骤准备输入。
2. 跑 L0 与 L1 两条基线，记录你自己的数字。
3. 与你看到的声明对比。差异超过 20% 就是有效证伪信号。
4. 如果在你机器上结论反过来了，那大概率是输入分布不同——把这个信息
   反馈成 issue，比争论「谁对」有用。

我们欢迎证伪，因为一个能被证伪的声明才有信息量。

## 家族级设计原则

### 原则一：零第三方依赖，不是审美是方法论

只允许标准库。这条约束的代价很实在：不能用好用的库，代码会长一些，
性能不会最优。收益同样实在：

**责任边界清晰。** 出问题时，只有两种可能：我的逻辑错了，或者标准库的语义
和我理解的不一样。没有第三种「某个依赖的某个版本改了行为」。

**可批评性。** 批评者不需要先花两小时配置环境。`python impl.py` 就能复现，
这让「我不信」变成「我跑给你看」。

** longevity。** 五年前的热门依赖，今天可能已经不再维护。零依赖的代码
十年后还能跑——这对参考实现是硬需求，因为参考实现的价值是长期被引用。

### 原则二：默认可证伪，负对照是入场券

每个 `selftest.py` 至少包含一个正对照和一个负对照。正对照证明「该通过的通过了」，
负对照证明「该失败的失败了」。

只有正对照的自检是自我确认，不是验证。举例：一个「静默失败检测器」，
如果只测「在有裸 except 的代码上能报出问题」，它可能只是一个「永远报错」的
实现——而永远报错的实现能通过所有正对照。必须再加一条「在干净代码上不报错」，
才能排除这种可能。

这条原则在工程上有个额外好处：它强迫作者想清楚「什么情况下这个机制**不该**触发」。
想不清楚这个，说明机制本身没定义好。

### 原则三：最小可跑，而不是功能齐全

每个实现刻意做小。宁可少做一个功能，也不要多写一百行看不懂的代码。

理由是参考实现的三个用途（可指着说、可当基线、可当靶子）都不需要功能齐全，
只需要**逻辑透明**。一个 300 行的实现，读者能在十分钟内读完并判断「这个方法
在我的场景里成不成立」；一个 3000 行的实现，读者只能选择相信或不信。

代价是明显的：这些代码不能直接用。所以每个仓都有「生产化改造清单」一节，
列出上生产前必须补的东西（错误处理、并发安全、性能优化……）。我们不假装
这是成品。

### 原则四：双向同步，避免两套真相

本仓库有两层结构：组合仓（55 个组件在一处）与独立仓（每个机制一个仓）。
同一份逻辑存在两份物理副本，这是**一致性风险**。

应对方式是机械的：独立仓的实现与组合仓的 `components/Pxx-*/impl.py` 必须
逐字节一致，任何修改两边同改。这条不是靠自觉，是靠检查——不一致会被
发布门抓到。

为什么接受这个冗余？因为两种结构满足不同需求。组合仓适合「我想一次看完」，
独立仓适合「我要引用这一个」。为了单一真相源而砍掉一种，会损失一半使用场景；
为了两种场景而允许两份代码漂移，会制造长期的维护债。机械同步是唯一可行的折中。

### 原则五：编号即契约

`P01`–`P55` 的编号一旦分配就不变。即使某个机制后来被重命名、被拆分、
被合并，原编号仍然指向原机制。

这条看起来是形式主义，实际是引用稳定性的基础。有人在文章里写了
「参考 EIM P13」，三年后这个链接必须还能指到同一个东西。编号变动会让
所有历史引用失效，而这种失效是静默的——没人会收到通知。

### 原则六：不隐藏失败

本仓库的每个 README 都有一节「失效模式」，明确写出这个机制在什么情况下
不管用。这一节不能写「无」——写「无」说明作者没想过。

写失效模式对作者是有心理成本的：等于自己拆自己的台。但这一节恰恰是
最有信息量的部分，因为它界定了机制的边界。一个没有边界的机制，等于一个
没有定义的机制。

### 这六条原则的冲突与取舍

它们会打架。比如「零依赖」与「最小可跑」在需要解析复杂格式时会冲突——
自己写解析器会膨胀代码量。我们的取舍是：宁可功能少一点，也不引入依赖，
因为依赖的长期成本高于功能缺失的短期成本。

再比如「双向同步」与「最小可跑」也冲突——同步机制本身是额外复杂度。
取舍是：把同步做成构建期的一次性拷贝 + 门禁检查，而不是运行时的动态加载。
把复杂度放在构建期，是这类问题的一般解法。

## 20 个常见误解与纠正

这一节收集的是我们在讨论「涌现智能」时反复遇到的错误前提。每一条都写成
「误解 / 为什么错 / 正确理解」三段，因为只纠正结论不改前提，下次还会错。

### 误解 1 · 涌现是玄学，无法工程化

**为什么错**：把「无法预测」当成了「无法观测」。天气也无法精确预测，
但气象站是工程。涌现同样：你不知道它什么时候出现，但可以在它出现时抓到它。

**正确理解**：可工程化的不是「制造涌现」，而是「观测、隔离、复现、接口化」
这四步（见理论框架一节）。这四步全是具体工序，没有一步需要玄学假设。

### 误解 2 · 模型越大涌现越多，所以换大模型就行

**为什么错**：这句话把「能力上限」和「能力可用性」混为一谈。大模型可能有
更强的能力，但如果你没有观测手段，你不知道它什么时候用上了这个能力、
什么时候没用、什么时候用错了。

**正确理解**：换模型提升的是上限，机制提升的是**可用比例**。一个能观测、
能路由、能验证的系统，可以让小模型发挥出接近大模型的稳定表现——
这在成本上比直接换大模型划算得多。

### 误解 3 · 涌现能力一旦出现就不会消失

**为什么错**：能力会退化，而且退化通常是静默的。换版本、改 prompt、
调整工具集，都可能让一项以前稳定的能力消失，而你的测试集恰好没覆盖它。

**正确理解**：能力是**需要看护的状态**，不是一次性获得的资产。这也是为什么
`P10 capability-regression-sentinel` 与 `P49 capability-drift-meter` 存在——
它们是能力的体检机制，不是锦上添花。

### 误解 4 · 多智能体一定比单智能体强

**为什么错**：多智能体引入了新的失败模式：共识幻觉（大家都错所以没人验）、
责任分散（出错了不知道谁的锅）、成本放大（N 倍调用）。如果任务本身不需要
分工，多智能体是纯粹的负债。

**正确理解**：多智能体的收益来自**独立性**，不是来自数量。只有当多个智能体
能提供**互不相关的判断依据**时，合议才有价值。共享同一个模型的五个 agent
投票，等于同一个错误投五票。

### 误解 5 · 反思总是有益的

**为什么错**：反思的成本是双份推理，收益不确定。在简单任务上反思是纯浪费；
在已经正确的答案上反思可能把它改错（over-thinking 是真实存在的失效模式）。

**正确理解**：反思的价值取决于**触发时机**，不取决于反思本身的深度。
这就是 `C10 反思触发` 一整簇存在的理由：先解决「什么时候想」，再谈「想多深」。

### 误解 6 · 更多 token 就是更准

**为什么错**：token 与准确率的关系不是单调的。在信息已经足够时，更多 token
只会增加干扰项与自相矛盾的概率。长思维链里出现「前面说 A，后面说非 A」
是常见现象。

**正确理解**：存在一个**边际收益归零点**。`P02 token-budget-thought-allocator`
与 `P38 reflection-budget-governor` 做的就是找这个点，而不是无脑加预算。

### 误解 7 · 静默失败是小事，反正有日志

**为什么错**：静默失败的定义就是**日志里看不出来**。异常被捕获后返回默认值，
日志可能只记了一行 warning，甚至什么都没记。等到下游出问题时，
根因已经隔了十几层。

**正确理解**：静默失败的危害在于它**污染了事实**。一个崩溃的系统你知道它坏了；
一个静默失败的系统，你基于错误数据做了十个决策才发现。这是家族里
把 `C04` 单列一簇的原因。

### 误解 8 · 多数一致就是正确

**为什么错**：一致性度量的是「相关性」，不是「正确性」。多个智能体用同一个
模型、同一份上下文，它们的「独立判断」其实是同一个判断的多次采样。

**正确理解**：合议的价值 = 独立性 × 个体准确率。独立性为零时，合议价值为零。
所以 `P47 role-isolation-tester` 这种「检查角色是否真的隔离」的工具，
比「增加投票者」更关键。

### 误解 9 · 记忆越多越好

**为什么错**：记忆的成本不只是存储，还有**检索噪声**与**过期污染**。
一条三年前的错误记忆被召回，比没有记忆更糟。

**正确理解**：记忆的核心指标不是「召回率」，是「精确率 × 时效性」。
`P25 drift-aware-consolidator` 与 `P26 cite-or-abstain-memory` 分别处理
过期与幻觉两个方向。宁可少记，不可记错。

### 误解 10 · 压缩一定丢信息

**为什么错**：压缩丢的是**冗余**，不是信息。自然语言在智能体之间传递时
冗余度极高（客套、重复、格式）。去掉冗余后信息量不变，成本下降。

**正确理解**：关键判据是**可还原性**——压缩后的表示能否重建出原意。
`P05 agent-lingua-compressor` 的设计前提就是这个：压缩必须可逆，
不可逆的压缩叫有损摘要，风险等级不同。

### 误解 11 · 形式验证的成本高到不现实

**为什么错**：从零写证明确实极贵。但如果有 fuzz 语料作为原料，
让机器先写证明骨架、人只做审核，成本结构完全不同。

**正确理解**：`C05` 这一簇的价值不是「让所有人做形式验证」，而是
**把已有测试资产二次利用**。你已经写了三年测试，那些反例里藏着引理。

### 误解 12 · 智能体之间发展出自己的语言是科幻

**为什么错**：这是被反复观测到的现象，不是什么未来设想。当两个智能体
被要求高效传递信息时，它们会自发缩短表达、建立约定。

**正确理解**：真正的问题不是「会不会发生」，而是「发生了你看不看得懂」。
看不懂的协议意味着你失去了对系统的可观测性——这才是风险所在。

### 误解 13 · 自进化就是自动调参

**为什么错**：调参改的是数值，自进化改的是**结构与策略**。调参不会让系统
学会新技能，只会让它在已知技能上更优。

**正确理解**：结构变更的风险比数值变更高一个数量级，因为它不可逆性更强、
影响面更广。所以 `C03` 的四道关（门控、哨兵、审计、回滚）不是过度设计，
是结构变更的最低要求。

### 误解 14 · 零依赖意味着性能差

**为什么错**：这些机制的性能瓶颈通常不在实现，而在**被观测的对象**
（模型调用、IO）。用 numpy 加速一个占总耗时 0.3% 的环节，收益可以忽略。

**正确理解**：零依赖牺牲的是复杂算法的可实现性，不是性能。在需要重计算
的场景（比如大规模向量检索），本仓库的实现确实不够，README 里也标了。

### 误解 15 · 参考实现没有实用价值

**为什么错**：参考实现的三个用途（可指着说、可当基线、可当靶子）都不需要
它达到生产质量。相反，生产质量的实现往往因为太复杂而无法被批评。

**正确理解**：参考实现的价值在于**降低讨论成本**。有了可运行的代码，
「我觉得这个方法不行」可以变成「我在第 3 步看到了这个问题」。

### 误解 16 · 指标可以量化一切

**为什么错**：可量化的往往是容易测的，不是重要的。维护成本、理解成本、
误导风险，都很难用 token 或延迟衡量。

**正确理解**：指标的作用是**排除明显无效**，不是**证明有效**。
通过了指标只说明「没有明显问题」，距离「值得用」还有判断。

### 误解 17 · 负对照是学术洁癖

**为什么错**：没有负对照的实验，无法区分「方法有效」与「方法永远返回真」。
一个永远报错的检测器，能通过所有「该报错时是否报错」的测试。

**正确理解**：负对照是**排除退化解**的唯一手段。这也是本仓库把
「负对照必须有」写成硬约束的原因。

### 误解 18 · 可复现就是「能跑起来」

**为什么错**：能跑起来只证明没有语法错误。可复现指的是**输出一致**——
同样的输入，跑两次得到同样的结果，且结果与记录一致。

**正确理解**：所以每个仓都有 `golden_output.txt`。它是行为契约：
代码改了导致输出变化，自检立刻红。这比「能跑」严格得多。

### 误解 19 · 机制越多系统越强

**为什么错**：机制之间有交互成本。55 个机制全开，可能互相干扰——
路由说跳过思考，反思说该重想，预算治理说没额度了。系统会在内部打架。

**正确理解**：机制的价值在**组合性**，不在数量。选 3 个能串起来的，
胜过装 30 个各自为政的。这也是为什么本仓库按簇组织而不是一堆散件。

### 误解 20 · 这套东西可以替代评测

**为什么错**：相反，这套东西**依赖**评测。没有基线，所有收益声明都是空的。

**正确理解**：这个仓库提供的是**被评测的对象和测量口径**，不是评测结论。
结论必须由你在自己的场景里跑出来。谁说「用了这个就变强了」，
谁就该被要求出示三层基线的数据。

## 三种角色的使用路径

这个仓库对不同的人有不同的入口。下面按角色给出最短路径，避免「打开 README
看到 55 个条目就关掉」这种常见结局。

### 角色一：学习者——想知道「涌现智能」到底指什么

**建议路径**：先读本节的家族总纲与理论框架（约 20 分钟），再挑 3 个实现读代码。

**为什么是 3 个而不是 55 个**：三个不同类型覆盖三种涌现，读三个就能建立
分类框架，剩下的 52 个只是同类变体。

**推荐的三个**：

- `P13 silent-except-scanner`（失败涌现，最短，30 行能读完）
- `P01 no-think-draft-agreement-router`（能力涌现，能立刻理解「省 token」的机制）
- `P50 surprise-bench`（度量涌现，理解「怎么知道自己不知道」）

**读完应该能回答**：为什么「静默失败」比「崩溃」危险？为什么「一致性分数」
能当路由信号？为什么「意外度」比「答对率」更能反映涌现？

**不要做的事**：不要一开始就试图理解 14 簇的关系图。那张图是结果，不是入口。

### 角色二：集成者——想在自己项目里用上某一个

**建议路径**：按问题找簇 → 读该机制的 TL;DR 与边界 → 读集成指南 →
复制 `impl.py` 到自己项目 → 按「生产化改造清单」补强。

**关键动作是第二步「读边界」**。跳过边界直接复制，是这类参考实现最常见的
误用方式。每个机制的边界一节都写了「禁用条件」，那些条件就是为你准备的。

**集成时最常踩的三个坑**：

一是把参考实现的阈值当默认值用。所有阈值都是「示例值」，在你的数据分布上
大概率要重调。README 里每个阈值都标了调参方向。

二是忽略输出格式的稳定性。参考实现的输出是给人看的（`print` 出来），
生产集成时应该改成返回结构化数据，而不是解析打印文本。

三是把「能跑」当成「能上」。`python impl.py` 跑通只证明逻辑成立，
不证明它能处理你的边界输入。

**建议的验证动作**：集成后，先用该机制的「可复现实验」跑一遍，
确认在你的环境里结论一致，再上。不一致就先查输入分布。

### 角色三：研究者——想评估这些机制是否真的有效

**建议路径**：直接看「统一评测协议」→ 挑你关心的机制 → 跑三层基线 →
看「可复现实验」的判据是否合理 → 提出证伪。

**你可以直接攻击的三个点**：

一是**指标选择**。我们选的指标（token、延迟、误报率、检出数）是否覆盖了
真实成本？很可能不覆盖——比如「维护成本」就没法用这些指标衡量。

二是**基线强度**。L1 基线（朴素启发式）是否足够强？如果我们的机制只是
打赢了一个很弱的启发式，那结论应该打折。

三是**外部效度**。所有实验都在小规模合成输入上做。真实系统的输入分布更脏、
更长、更不规则。这个差距是真实的局限，我们不掩饰。

**欢迎的贡献形式**：不是「我觉得不对」，而是「我在 X 场景下用 Y 输入跑，
得到 Z 结果，与你的声明差 W」。后者可以被回应，前者不能。

## 一次完整的涌现审计：从零到报告

这一节把前面所有内容串成一个可执行流程。假设你接手一个已经跑了一段时间的
AI 系统，想知道「它到底有什么涌现行为、哪些是好的、哪些是隐患」。
下面是六个阶段，每个阶段标注用哪些机制、产出什么。

### 阶段 0 · 定边界（不做会白忙）

先回答三个问题，写下来：

1. **系统边界在哪**：哪些调用算系统内部，哪些算外部？边界不清，
   后面所有观测都会串味。
2. **什么算「好」**：是准确率、成本、还是稳定性？三者的优化方向经常冲突，
   必须选一个主目标。
3. **可接受的观测成本**：能加多少额外调用、多少延迟？这决定你能用多重的探针。

产出：一页纸的审计范围说明。没有这一页，后面必然发散。

### 阶段 1 · 观测（用 C13 与 C04）

**静态观测**：先跑 `P13`–`P16` 四个猎手，扫代码层。
这一步不需要任何运行时数据，成本最低，往往能立刻发现问题。
产出：代码级问题清单。

**动态观测**：用 `P48 emergence-probe-suite` 设计一组探针，重点不是
「测它会不会」，而是「测它在边界输入上的表现是否稳定」。
配合 `P50 surprise-bench` 记录「模型自己有没有预料到会答对」。

**协议观测**（如果有多智能体）：用 `P06 emergent-protocol-discoverer`
从交互日志里挖重复模式，看是否已经形成内部约定。

产出：一份观测清单，标注「已确认的涌现行为」与「疑似但未确认」。

### 阶段 2 · 度量（用 C13）

给每个候选行为建一条基线。做法：

1. 记录当前指标（成本、延迟、准确率、误报率）。
2. 用 `P49 capability-drift-meter` 建立能力快照，作为后续对比的锚。
3. 明确每个指标的测量条件（输入规模、任务类型、重复次数）。

产出：一张基线表。这张表是后面所有「改进」的参照物，必须诚实——
基线虚高会让后续所有改进看起来都无效。

### 阶段 3 · 干预（按簇选机制）

不要一次装十个机制。按「问题 → 簇」映射，一次只装一个：

| 观察到的问题 | 该用的簇 | 起手组件 |
|---|---|---|
| 成本高但任务简单居多 | C01 思考路由 | `P01` 或 `P03` |
| 多智能体消息冗长 | C02 涌现语言 | `P05` 先压缩，`P06` 先观测 |
| 改自己后能力下降 | C03 自进化护栏 | `P10` 哨兵先建，再谈改 |
| 测试全绿但线上出错 | C04 静默失败 | `P13`+`P15` 先扫 |
| 状态错乱、说不清当前处境 | C06 世界模型 | `P20`+`P22` |
| 记错了还坚信 | C07 记忆溯源 | `P26` cite-or-abstain |
| 反复想同一件事 | C10 反思触发 | `P37` 卡住检测 |
| 技能库越来越乱 | C11 技能涌现 | `P41` 去重先做 |

产出：一个机制 + 一个明确预期（预期必须是可量化的）。

### 阶段 4 · 验证（三层基线）

按评测协议跑 L0/L1/L2。关键动作是**跑负对照**，并且**重复 5 次**。

判定规则（提前写死，不许事后调整）：

- 相对改善 ≥ 预设阈值，且 5 次范围不跨零 → 记为有效。
- 改善存在但范围跨零 → 记为「不确定」，不许写成有效。
- 没有改善甚至变差 → 记为「无效」，如实记录。

产出：每个机制一行四段式结论（指标/条件/代价/判据）。

### 阶段 5 · 固化（用 C11）

有效的机制要固化下来，否则下次还要重新发现。固化时做三件事：

1. **命名**：给它一个稳定的编号/名字，写进团队文档。
2. **去重**：用 `P41 duplicate-skill-detector` 检查是否与已有机制重复。
3. **加守护**：用 `P10 capability-regression-sentinel` 给它配一条回归检查，
   防止未来某次改动把它弄坏。

产出：更新后的机制台账。

### 阶段 6 · 出报告（固定格式）

报告必须包含五节，缺一节即不完整：

1. **范围**：审计了什么、没审计什么。
2. **基线**：改前的数字，含测量条件。
3. **发现**：确认的涌现行为清单，分「良性 / 隐患 / 未知」三类。
4. **干预结果**：每个机制的四段式结论，含无效的。
5. **遗留**：没解决的问题、不确定的结论、下一步建议。

**一条硬规则**：报告里「无效」的条目必须保留。删掉无效结果会让整份报告
变成宣传材料，而宣传材料没有决策价值。

### 这个流程的常见失败点

**失败点一：跳过阶段 0**。没有主目标，后面每个机制的收益都无法判断，
最后变成「装了一堆，感觉好了一些」——这种结论不可复用。

**失败点二：基线造假（无意的）**。用最差的配置当基线，显得改进巨大。
正确做法是用当前生产配置当基线，哪怕它已经不错。

**失败点三：一次装多个机制**。收益无法归因，出问题无法定位。
一次一个，慢但可归因。

**失败点四：不留负结果**。所有人都想报告成功，但负结果才是让团队
不重复踩坑的信息。这一条最难做到，也最重要。

### 时间预算参考

一个中等规模系统（10 个左右的 LLM 调用点）的完整审计，粗算：

- 阶段 0：半天（但值得花一天）
- 阶段 1：1–2 天（静态快，动态慢）
- 阶段 2：1 天
- 阶段 3+4：每个机制 0.5–1 天（这是大头）
- 阶段 5+6：1 天

总预算 1–2 周，取决于装几个机制。如果只做静态观测（阶段 1 的前半），
半天就能出第一份清单——建议从这里开始，先拿到正反馈再投入。

## 家族术语总表

55 个组件各自有术语表，但有些概念跨簇通用。这里统一口径，避免同一个词
在不同 README 里含义漂移——这是多仓结构最容易出的隐性错误。

| 术语 | 英文 | 在 EIM 里的确切含义 |
|---|---|---|
| 涌现 | emergence | 系统未被显式编程却稳定表现出的行为模式。三个限定词缺一不可：未编程、稳定、成类。 |
| 人工化 | artificialization | 把涌现现象变成工程对象的四个动作：命名、隔离、复现、接口化。这是本仓库唯一的动作主张。 |
| 机制 | mechanism | 一个有明确输入输出、可独立运行、有已知失败模式的最小功能单元。55 个机制即 55 个这样的单元。 |
| 簇 | cluster | 3–5 个共享同一观测对象、接口形状一致的机制的集合。14 簇是家族的中层结构。 |
| 参考实现 | reference implementation | 逻辑透明优先于功能齐全的实现。能跑、有断言、有快照，但不保证生产可用。 |
| 最小可跑 | minimal runnable | 单文件、零依赖、一条命令能出结果。这是「可批评性」的物理前提。 |
| 正对照 | positive control | 实验里「应该通过」的那条路径。证明机制在该触发时确实触发了。 |
| 负对照 | negative control | 实验里「应该不触发 / 应该失败」的那条路径。排除「永远返回真」这类退化解。 |
| 快照门 | golden test | 用发布时的真实输出作为行为契约。代码改动导致输出变化即判红。 |
| 三层基线 | three-tier baseline | L0 无机制、L1 朴素启发式、L2 已有最优。只跑 L0 的对比不算实验。 |
| 静默失败 | silent failure | 出错后不报告、返回貌似合理的默认值、让下游以为正常的失效方式。危害在于污染事实。 |
| 涌现语言 | emergent language | 多个智能体自发形成的、比自然语言更短的内部约定表示。核心风险是不可观测，不是不可用。 |
| 过程奖励 | process reward / PRM | 对推理中间步骤独立打分的能力。用于决定「继续算还是停」，前提是任务可步级评估。 |
| 可证伪 | falsifiable | 能构造出具体的、可执行的反驳场景。做不到这一点的机制在本仓库不予收录。 |
| 双向同步 | bidirectional sync | 独立仓与组合仓的同一份实现必须逐字节一致，任何修改两边同改，由门禁检查。 |
| 署名锚 | citation anchor | 一个可被单独引用、单独开 issue、单独打星的稳定地址。编号就是锚的键，永不复用。 |
| 退化解 | degenerate solution | 不做任何判断却总返回同一结论的实现（如永远报错）。负对照专门用于排除它。 |
| 接口窄化 | interface narrowing | 一个组件只做一件事。窄接口的失败模式可枚举，宽接口的失败模式无穷。 |
| 元层 | meta layer | 度量其他机制是否有效的那些机制（C13）。没有元层，其余 52 个机制的收益不可证。 |

> 如果某个组件 README 里的用法与上表冲突，以上表为准，并把该组件标为待修。

## 贡献、治理与许可

### 贡献流程

**问题报告优先于代码贡献。** 一个机制的失效场景报告，比一个功能 PR 有价值得多。
报告请包含：输入、期望、实际、你的环境。没有这四项的报告很难被处理。

**代码贡献的三条硬要求**：

1. **零新增依赖**。引入任何第三方包会被直接拒绝，没有例外。
2. **必须带负对照**。新增或修改 `selftest.py` 时，负对照不能删、不能弱化。
3. **双向同步**。如果改的是独立仓，必须同时改组合仓对应组件（或反之），
   并在 PR 描述里注明。

**文档贡献同样重要。** 发现某节写得看不懂、某个失效模式没写全、
某个实验步骤复现不出来，都是有效贡献。文档的准确性直接决定这个仓库的价值。

### 裁决原则

当出现分歧（比如「这个机制该不该收」「这个收益声明是否成立」），
裁决依据是**可复现性**，不是多数票，也不是作者资历。

具体做法：主张方提供可复现步骤，反对方按步骤复跑。谁的结果能被第三方
独立复现，谁的主张成立。复现不出来的主张，无论多合理，都不采纳。

这条规则会让一些「感觉上对」的想法被拒。这是刻意的代价——一个宁可拒绝
好想法也要保持可核验的仓库，长期价值高于一个什么都说好的仓库。

### 收录标准

一个新机制要被收录，必须同时满足：

**与已有机制不重复。** 判断标准是「输入输出形状是否相同且逻辑是否可归约」。
仅仅是换了个名字、换了个阈值、换了个应用场景，不算新机制。

**有明确失败模式。** 说不清什么情况下失效的，说明边界没想清楚。

**能独立运行。** 必须零依赖、单文件、可 `python xx.py` 直接跑。

**收益可测。** 至少要有一个可量化的指标，哪怕只在合成数据上。

这四条都在「可复现实验」与「失效模式」两节里有对应段落。写不出来就是没达标。

### 版本与退役

**版本策略**：家族版本用 `EIM-x.y`。新增机制升 minor，破坏性变更（改接口、
改编号语义）升 major。编号本身永不复用。

**退役机制**：机制可能被证伪、被更好的实现取代、或者被发现前提错误。
退役不删除，而是标记 `deprecated` 并在 README 顶部说明原因。
删除会让历史引用失效，这比留着一个明确的废弃标记更糟。

**退役的三种合法理由**：一是被更强基线击败且差距显著；二是前提被证伪
（比如某个假设在实测中不成立）；三是发现与已有机制实质重复。
「没人用」不是退役理由——参考实现的价值不取决于使用量。

### 许可边界

**代码：Apache-2.0。** 允许商用、修改、闭源再分发。要求保留版权声明与
许可文本，并注明修改。不提供专利报复条款之外的限制。

**文档与规范：CC BY 4.0。** 允许转载、改编、商用。要求署名。

**「声明符合」的含义**：如果你在文档、产品页或论文里声称「符合 EIM-1.0」
或「兼容 EIM-1.0」，则必须署名。署名格式：

```text

```

**不声明则无需署名**：直接使用代码、改造代码、把思路用在自己的系统里，
都不构成「声明符合」，无需署名。这条边界是刻意放宽的——我们希望这些
机制被自由使用，署名只用于「引用来源」这个场景。

**为什么用双许可而不是单一许可**：代码和文档的合理使用边界不同。
代码需要专利授权与免责条款，文档需要署名与改编权。用一套许可覆盖两者，
总有一边不合适。

### 治理的自我限制

这个仓库没有基金会、没有委员会、没有 RFC 流程。裁决由维护者做，
依据是上面写的可复现性原则。这套治理很轻，也意味着它依赖维护者的判断质量。

如果有人愿意把它做成更正式的社区项目，我们欢迎——但在那之前，
保持轻量比假装有治理结构更诚实。
